# I20: Add the independent spec-conformance reviewer

## Parent spec or request

`docs/specs/phase-33/001-change-risk-review-assurance.md`

Owner request of 2026-08-02: adopt the Spec axis from the supplied two-axis
review pattern, without adopting its Standards axis.

## Intent summary

Give Codex and Claude a generated, independent `spec-conformance-reviewer`
that compares the complete change since a fixed point with the governing
documented intent. It reports code-versus-intent drift separately from both
code-quality and change-risk findings, so a spec defect cannot disappear in a
shared priority queue.

## Evidence

PR #148 produced three spec-conformance misses that the existing review
pipeline found only incidentally:

1. A derived count changed from 44 to 45; the test oracle changed while the
   owner-approved acceptance criterion remained 44.
2. The review-learning README was corrected, but two TypeScript comments kept
   asserting the falsified `findingId` rationale.
3. The README promised that `findingId` rendered in evidence headings and
   table cells, while `renderReviewLearningRecordV1` rendered it only in
   headings.

These are three forms of the same gap: missing or partial requirements,
unrequested behavior, and apparently implemented requirements whose behavior
is wrong.

## Behavior slice

For every profile that qualifies for the generated subagent-driven workflow,
emit a `spec-conformance-reviewer` definition for supported Codex and Claude
targets. Follow the existing `change-risk-reviewer` source-and-emission pattern:
the compiler owns the source template, generated definitions are emitted into
`.claude/agents/` and `.codex/agents/`, and repository self-application plus
golden fixtures commit the regenerated bytes. Generated reviewer artifacts are
never edited by hand.

Replace the generated workflow's generic `spec-reviewer` invocation with this
reviewer while preserving the existing order:

`implementer -> spec-conformance-reviewer -> code-quality-reviewer ->
change-risk-reviewer -> final-review`.

The workflow pins one caller-supplied fixed point, resolves it before review,
and reviews the three-dot accumulated change against the merge base. The
review context contains:

- the resolved fixed point, head, diff command or equivalent existing local
  snapshot seam, and commit list;
- the originating issue brief, its parent spec and approved amendments, and
  every applicable MUST, non-goal, acceptance criterion, error contract, and
  documented behavior claim;
- repository instruction precedence needed to decide which intent is
  authoritative; and
- local instructions for reading the entire diff and any unchanged source,
  test, generated artifact, or documentation needed to verify a claim.

Spec-source discovery is deterministic: use the linked ledger brief first,
then its declared parent spec and approved amendments; include an explicitly
supplied path when present. Commit-message or branch-name guessing may locate
a candidate only when the ledger link is unavailable. If authoritative intent
cannot be identified, return `NEEDS_CONTEXT`; absence of a spec is never a
clean result.

The reviewer is clean-room with respect to implementation claims: it receives
the change and governing intent, but not the implementer report, prior praise,
code-quality findings, change-risk findings, or their rankings. It is
review-only and performs no writes.

The reviewer returns one closed Spec-axis result with status
`COMPLIANT | ISSUES_FOUND | NEEDS_CONTEXT`. Each finding has exactly one of
these classes:

- `missing-or-partial`: a requirement is absent or only partly implemented;
- `unrequested-behavior`: behavior in the change is outside the approved
  intent or contradicts a non-goal; or
- `implemented-wrongly`: the change appears to implement the requirement but
  its observable behavior, tests, comments, documentation, generated output,
  or reachable consumers do not match it.

Every finding quotes the governing spec or brief line and cites its exact
document path and line range, then cites the conflicting implementation
evidence. A finding also states the expected behavior and the concrete drift.
The validator rejects an issue without both sides of that comparison. A clean
result requires an explicit requirement-to-evidence coverage summary; updated
tests alone are not authoritative evidence when they disagree with approved
intent.

Spec findings remain in a dedicated result and remediation handoff. They are
never converted to `ChangeRiskFindingV1`, merged into the change-risk queue,
or reranked against P1/P2/P3. The change-risk reviewer receives neither the
Spec result nor its finding list. The code-quality reviewer keeps its current
maintainability objective and receives no Fowler-smell or new Standards-axis
rubric from this slice.

When remediation names one field, comment, assertion, renderer, or call site,
the owner must fix the defect class or state why a class-level fix is not
practical, following I18. Before introducing any helper, the implementer must
check for and reuse an applicable exported helper, following I17.

## Non-goals

- Adding a Standards axis, Fowler-smell baseline, or general style review.
- Merging, deduplicating, reprioritizing, or choosing a winner between Spec
  and change-risk findings.
- Reviewing whether a specification is well designed before implementation;
  Phase 34 owns bounded pre-implementation spec review.
- Broadening the change-risk reviewer's objective or typed envelope.
- Hand-editing `.claude/agents/` or `.codex/agents/`.
- Changing product runtime behavior, profile schema, or generated user config
  outside reviewer/workflow artifacts.
- Uploading source, requiring GitHub, or using a hosted review provider.

## Acceptance criteria

- Qualifying Codex and Claude outputs contain a generated
  `spec-conformance-reviewer` with no dangling workflow reference;
  non-qualifying profiles remain byte-identical.
- The generated subagent workflow invokes it after implementation and before
  code-quality review, and no longer relies on the generic `spec-reviewer` for
  this conformance gate.
- A bad or missing fixed point fails before review; a missing authoritative
  spec produces `NEEDS_CONTEXT`; neither case can produce `COMPLIANT`.
- The prompt and result contract cover exactly the three finding classes in
  this brief.
- Every finding requires an exact spec/brief quote with document path and line
  range plus conflicting implementation evidence.
- Focused fixtures reproduce all three PR #148 instances and yield the
  expected finding class; the 44-to-45 fixture proves that changing the test
  oracle does not silently redefine the approved criterion.
- A compliant fixture exercises the coverage summary and reports no findings.
- Negative contract tests reject missing quotes, missing spec locators,
  missing implementation evidence, unknown finding classes, and
  `COMPLIANT` results without complete coverage.
- Spec findings are stored and remediated independently: tests prove they are
  neither rendered into nor ranked against `ChangeRiskResultV1` findings.
- Clean-room tests prove the Spec reviewer does not receive implementer
  claims, prior review findings, or change-risk priorities.
- Projection or golden tests prove the reviewer contains no Standards/Fowler
  rubric and the code-quality reviewer remains unchanged.
- Source templates are changed and regenerated artifacts are committed;
  I14's committed-byte and path-set guard passes.
- Before adding a new fixed-point, diff, line-location, or rendering helper,
  implementation evidence identifies the existing exported helpers examined
  and reuses an applicable one.
- Fixes for the three regression fixtures cover the named defect class or
  record why a class-level correction is not practical.
- Focused tests pass, then golden tests, `npm run check`, and any applicable
  doctor/pack verification all exit 0.

## Dependencies

Depends on Phase 33 I1's generated reviewer emission pattern and I14's
self-applied-artifact guard. Sequence Phase 33 I6 after I20 so published
workflow validation exercises the adopted Spec axis.

## Parallelism notes

Not parallel-safe with other changes to compiler reviewer emission,
`subagent-driven-change`, shared reviewer fixtures, or self-applied artifacts.

## Contract impact

Adds the generated `spec-conformance-reviewer` and a closed Spec-axis result
contract. Changes the generated review pipeline's spec-conformance gate but
does not alter `ChangeRiskResultV1`, change-risk priority semantics, profile
schema, or runtime compilation outputs unrelated to reviewer/workflow files.

## Security impact

Review remains local, read-only, network-independent, and secret-denied.
Evidence quotes the minimum governing intent and locates implementation code;
it must not reproduce secrets or raw source beyond the minimum needed to
identify the drift.

## Documentation impact

Document the new generated reviewer and the distinct purposes of Spec,
code-quality, and change-risk review. State explicitly that no Standards axis
was adopted and that Phase 34 reviews spec quality before implementation while
I20 reviews implementation conformance after it.

## Review expectations

Build a spec-to-test matrix for every MUST and acceptance criterion above.
Independently verify that the three PR #148 fixtures fail for the intended
reason, that the Spec result never enters the change-risk queue, and that
regenerated bytes rather than hand-edited artifacts carry the change. Treat
any new helper as suspect until indexed search proves no suitable exported
helper exists. Require class-level remediation for every validated finding.
